# Sentinel

Self-hosted officer of the watch: review requests sorted into lanes, your own PRs by what they wait for, the PRs you approved followed until they have landed (merged + post-merge checks green), provider status pages, the Claude Code sessions running on the host filed under their tickets (Sessions), optional Cycle objectives, an optional tech watch (Lookout) — local Docker, web UI on `localhost:8300`, Web Push, optional Claude agents through a host bridge and a Claude Code mod reading `/api/summary`.

**Design (14/10/2026): an inbox, one item at a time.** Sidebar (Inbox, Sessions, Cycle, Watch, Lookout, the status light, Settings) + list pane + detail pane, like a native macOS app at night: four surface steps (`--bg` → `--pane-3`) and hairline shadows for depth, system font (SF Pro), SF Mono for refs and diffs, 8–12 px radius. Colour says what something is: blue = waits on you / selection / primary action, red = broke, orange = needs a look, green = good news, terracotta = Claude. The list has three tabs: **Priority** (the Second's plan for the day, your Claude Code sessions waiting on you, monitoring alerts, the Second's fixes, reviews for you, follow-up problems, your PRs one row per cause), **Later** (snoozed, team requests in grace, bumps, status pages, reminders, what is landing after your approval, your PRs waiting on others), **Done**. Two triage actions only: **Done** (ack until it changes) and **Later** (snooze until tomorrow 9:00). Keyboard: `↑↓`/`j k`, `E`, `L`, `⏎`. No gradient beyond the logo, no emoji, no CSS framework. Tokens at the top of `static/style.css` — keep new UI inside them.

## Stack

- **Backend**: Flask 3 + Gunicorn (python:3.12-slim) — **exactly 1 worker** (`-w 1 --threads 8`): APScheduler runs in-process, more workers = duplicated jobs
- **Frontend**: Jinja2 + HTMX 2 (CDN with SRI) + Google Fonts, no build step
- **State**: SQLite `/data/sentinel.db` (WAL), `./data/` volume
- **Notifications**: Web Push (pywebpush + VAPID), service worker `sw.js` served at the root

## Triage model (engine.py)

Every `WatchedItem` has a **lane** (where it shows: `plan`, `session`, `fix`, `you`, `team`, `deps`, `mine`, `followup`, `incident`, `watch`, `cycle`, `health`) and an **urgency**:
- `now` → pushed when it appears, again when its fingerprint changes after an ack
- `later` → pushed only if still pending after its lane's grace (`promote_due()`, every minute): `triage.team_grace_minutes` for team review requests, `session_wait_minutes` for a session waiting on you; resolved meanwhile = never pushed
- `quiet` → never pushed (bumps, drafts, maintenance, reminders)

"Needs you" = `db.ATTENTION`: pending and (`now`, or `later` already notified). Badges count **decisions** in the inbox lanes (`main.INBOX`: plan, session, watch, fix, you, team, followup, mine — health is the sidebar light, cycle its tab, incidents wait in Later) (`main._units`): every item, except your own PRs which count once per cause (`_mine_groups`: action + first failing CI family). Your PRs approved and green (`merge`) are listed, never pushed (`my_prs.LISTED`). A post-merge failure whose follow-up run says `unrelated` is cleared (`_clear_by_claude`): it leaves "needs you" for Later.

State machine: `pending` → `acked` (re-opens when the fingerprint changes unless `ack_forever`, set by older versions only) / `snoozed` (`wake_snoozed()`, quiet items wake silently) → absent from `MISSES` (2) fetches in a row = `resolved` (`items.missed`; GitHub search drops PRs for a poll now and then — 17 PRs were re-pushed within 30 min before this) → reappearance = fresh cycle (`first_seen` reset). Fingerprints encode what should re-open an ack: `updatedAt` for direct reviews, the constant `team` for team requests (a team PR moving is still not yours), the target version for bumps, the action (+ failing CI families) for your PRs, a `days // stale_days` bucket for stuck approvals.

Guards: `promote_due()` and `wake_snoozed()` skip items missing from the last poll (`missed > 0`); a session row also needs to have been seen in the last minute (bridge away, Sentinel stopped or asleep: the wait may have been answered). `process(…, misses=1)` for a source whose list never drops rows (the sessions). More than `STORM` (3) notifications from one pass → one summary push. **First pass of a source** (no `seeded` flag in `watcher_state`) records without pushing and re-baselines old rows (`notified_at = first_seen`, acks moved to the new fingerprint) — an upgrade that changes fingerprints must not resurface everything. `promote_due()` ignores sources not seeded yet. `check_health()`: `db.record_run()` keeps `error_since` per source; every source failing longer than `triage.health_minutes` → **one** item `sources` (lane health, constant fingerprint: one push per outage — they fail together, 40 per-source pushes in two days before) shown as the sidebar light (`_status`).

Sources named from the config (`statuspage:<name>`, `grafana:<uid>[-<vars hash>]`) that left it are retired at start (`engine.retire`): their items resolved, their state dropped — a removed link must not wait forever or keep a failure lit.

## Follow-up (followup.py)

One GraphQL call: `reviewed-by:<login> -author:<login> author:app/<bot>…` open + closed within `window_days`, with the merge commit's check runs and its **first parent's** check runs. Post-merge checks = check runs whose workflow event is not `merge_group`/`pull_request*` + commit statuses. Stage: `waiting` (blocker, worst first: dismissed > conflicts > ci failing > changes requested > review required > draft > ci running > ready) · `checking` (pending, or merged < 30 min with nothing yet) · `failed` · `inherited` (every failing check was already failing before: on the parent commit, or — when the job did not run there, `paths` filters — in the previous run of its workflow on the base branch, `evidence.previous_outcome`, cached) · cancelled runs are neutral (`concurrency:` supersedes them) · `reverted` (a cross-referenced PR titled "Revert…") · `landed` · `no checks` · `closed`. Items: dismissed, stuck (`waiting_days >= stale_days`), failed, reverted. A `failed` PR merged less than `AUTO_INVESTIGATE_HOURS` (48) ago gets one `followup` agent run per merge commit — never on the source's first pass; older ones keep the Investigate button (no surprise push about the past). Pages read the stages through `main._followup_view`: `inherited` + failed-and-cleared-by-Claude = section "not yours", and every count (inbox, Later, badge) comes from it or from the engine items. `followup.cleared()` is the one clearing rule: verdict `unrelated` AND no open failure that passed right before the merge AND every open failure among the checks whose logs the run read (`investigated` in its context; an older run without it clears nothing) — a verdict alone can be steered, and a check that failed after the investigation was never judged. `_investigate` asks again when the set of failing checks changes (`settled(failing=…)`). A previous run GitHub could not return (`unknown`) keeps the last refresh's answer (`known`, absent included), else waits in `checking` for `UNKNOWN_MINUTES` (60, `unknown_since`) and then alerts as "absent" — no alarm on a hiccup, no silence when the API stays down. `previous_outcome` lists runs created before the failed one (`created=<…`), same event only, and caches only failure/success answers.

## Dependency bumps (deps.py)

A review request whose author is a Bot and whose title parses as a bump (or carries a renovate/dependencies label) goes to lane `deps`. The PR body is fetched once per (PR, title) for the update table: type (major > minor > patch), from → to. `pending_groups()` groups pending bump items by `name@to`; **Approve N green** (`POST /api/deps/approve {key, ids: "id:sha,…"}`) reviews only the PRs the page showed, still `approvable()` (green, not draft, not conflicting), whose head is still the sha the page showed (`github_pr.head_sha`), pinned with `commit_id` — the rest is reported back. `precheck()` (every 5 min) queues one `precheck` run per group (subject `deps:<name>@<to>`), PR URLs of every repo at once, and again when the set of PRs changes (`settled(urls=…)`).

## Claude agents (agents.py + contrib/claude-bridge)

`agent_runs` = one row per (subject, mode), subject = `owner/repo#n` or `deps:<key>`; `queue_run` re-queues, `tick()` (every 10 s) starts up to `agents.concurrency` runs in threads → `POST {bridge}/run {mode, url, urls, context}` with `Authorization: Bearer CLAUDE_BRIDGE_TOKEN`. Automatic modes obey `agents.precheck|followup` and `max_runs_per_day`, retry a failed run after an hour up to `MAX_ATTEMPTS` (3, `attempts` column); on-demand ones never do, and reset attempts. Their context is a callable (`deps.context`, `followup.context`): the GitHub fetches of the material only happen when a run is actually queued. `check_bridge()` (every 2 min) records `claude-bridge` in `watcher_state`: a bridge that does not answer, or an older one without this version's modes, becomes a health item. The page only names a subject: `_agent_target()` rebuilds URL and context from Sentinel's own data. Prompts start with `Verdict: <token>` (English tokens whatever `BRIDGE_LANG`): `agents.verdict()` reads the **first line only** (a verdict quoted from a log further down must not count) → (token, tone), `first_finding()` for rows, `summary_line()` for pushes. A finished `followup` run pushes its verdict (`_announce`). Every run passes `--setting-sources user`: the project/local settings of `BRIDGE_CWD` carry their own allow rules, which **add** to `--allowedTools` (verified 12/10/2026: an allowed `Bash(tee:*)` wrote a file). **Reading ahead** (`insight.refresh()`, every 5 min): `brief` per review request (subject `owner/repo#n`, settled on `head`), `whyred` per first failing CI family of your PRs (subject `why:<family>`, settled on the sorted `repo#n@head` list), `asks` per PR of yours with changes requested or open threads (subject `asks:owner/repo#n`, settled on changes_by + unresolved count); verdicts land on the list rows (`list_macros.claude_tag`) and in the detail. **Lookout** (below): `scout` and `assess` (subject `lookout`), `dig` on demand (subject `lookout:<id>`, `_agent_target` → `lookout.target`). `ON_FINISH[mode](run, output)` runs **before** the run reads done (lookout: its rows are still claimed while they are written); raising fails the run. `context["profile"]` is sent as the top-level `profile` — the reader's own words, the only text the bridge puts outside the fence. Toolsets: `precheck`, `followup`, `brief`, `whyred`, `asks`, `scout`, `assess`, `dig` = **no tool** (`--tools ""`), the material (built by `evidence.py`) arrives in `context` and the bridge fences **all** of it between BEGIN/END MATERIAL as untrusted (a custom prompt without `{context}` gets it appended); `deep` = named read-only commands, no `gh api` (`-f` POSTs, `-X` can follow any prefix), no WebFetch, offered only on PRs whose author is not a Bot. The bridge refuses non-local Host headers, runs nothing without `BRIDGE_TOKEN`, and `/healthz` reports `api` (5) and `token`: `check_bridge()` flags an older bridge or a missing token. The daily cap is one counter of automatic queues, retries and re-runs included (`agents.used_today`, `watcher_state` agents/day+count). The fence markers carry a per-run nonce (`BEGIN MATERIAL <nonce>`): the material cannot fake its end. `deep` may only `git fetch origin` and its Read tool refuses `.env`, `.mcp.json`, keys, `~/.ssh`, `~/.aws`, `~/.config` (a shell `cat` stays possible: a fence, not a vault — the remaining exfiltration path is a `gh … -R <host>` lookup). `reviews` (old table) is migrated into `agent_runs` at startup.

## Lookout (lookout.py)

`collect()` (every `collect_minutes`) runs `lookout_sources.jobs()` — one read per feed, trending language and repository (Reddit: one read for every subreddit, `r/a+b`; a second read right after gets a 429) — into `lookout`, one row per `canonical()` key: a repository is `github:owner/repo` whichever page of it is shared, other links lose `www.` and tracking parameters; a known key gets the new mention (`sources` JSON: source → discussion, points, comments), and a `dropped` one goes back to the scout when a source it was not seen on mentions it — traction shows as a second source. Only http(s) links are stored (rows render them as `href`). Per-source status lives in `watcher_state` (`lookout`, `source:<name>`) without `error_since`: a failing feed shows at the bottom of the page, never as a health item.

`advance()` (every 2 min, a few queries when idle): `_recover()` (rows claimed by a run no longer queued/running go back: `scouting` → `new`, `assessing` → `kept`), `_scout()` (all `new` rows up to `batch`, oldest first, at most every `scout_hours` — immediately when a full batch waits after a success), `_assess()` (`kept` rows by `assess_batch`, material fetched in the context callable: repository facts + README through `github.rest`, an article through `page_text`, a release's notes; `facts` saved for the page), `digest()`, `_forget()`. `_ready()` gates both: a failed run retries after an hour up to `agents.MAX_ATTEMPTS`, then waits `scout_hours` — a broken prompt must not eat the daily cap the other modes share. `apply_scout` / `apply_assess` (hooked through `agents.ON_FINISH`) need their verdict line (`scouted` / `assessed`) or nothing moves and the run fails; unknown ids are ignored, a row left out of an assessment is assessed without a score (never shown). Releases (`releases` source: minor/major, or a patch whose notes mention security/CVE) skip the scout. A **find** = assessed, score ≥ `threshold`, verdict not `skip` (`lookout.finds()`). Feedback (`useful`, `noise`, `known`, `try`) goes back into both prompts (last 40). The page follows the digest: *New since the last digest*, *In the last digest* (what Monday's push announced), *Earlier* (collapsed); *To try* = feedback `try` whatever the score (a threshold raised later does not empty it); *Filtered out* = the week's near misses (assessed under the threshold) first, then the most upvoted drops. Parsing accepts list items, numbers and bold (`1. **#12** — …`). `digest()`: once per `last_slot(digest)` (local `TZ`), the finds assessed in the week before the slot, one push, none without finds; the slot is recorded either way. `_forget()`: rows without feedback older than `keep_days`.

`page_text()` reads public addresses only (`public()`: every resolved address `is_global`), follows redirects itself and checks each hop, HTML only, 1.5 MB and 30 s max (a server dripping bytes must not hold the job), the `<main>`/`<article>` text when there is enough of it; a page that reads as a few words (Reddit's app shell) falls back to the summary — a self post's text is stored at collection. DNS rebinding can still beat `public()`; nothing leaves anyway: no tool, and `md.render` drops images. The Lookout prompts leave `{url}` out: a find's link is feed text, it travels in the fence like the rest — only `profile` is outside. The trending source is a third-party RSS mirror of github.com/trending (no API): when it breaks, its rows show as failing sources.

## Sessions (sessions.py + bridge `GET /sessions`)

**The context advisor owns a session's story and figures.** `contrib/claude-code-context` writes, on every refresh of its status line and at once on `/clear` or a resume (a new session id), `<CLAUDE_CONFIG_DIR>/context-advisor/<session id>.json` (`published()` in its core: story, pinned, project, tokens, answeredAt, cold, advise `cold|handoff|''`, nextUsd, freshUsd, its handoff command — `/handoff`, or `/context-handoff` when another plugin holds that name, a skill of the same name included); a session gets back the story published for it, when resumed or when the mod starts again (a reload or a respawn fires `session.start` with the module's state reset); `CONTEXT_STORY` links a session nothing was published for, as `/ticket` would (`pinned`). `contrib/claude-code-context/tests/published.ts` is the format: the advisor's test checks `published()` against it, `test_sessions.py` reads it. Sentinel shows that file as is — no story rule, threshold or price of its own — through `sessions._context()`: a field not written the way the advisor writes it reads as absent (its handoff command is typed into a live session). A session without the advisor lists without story or size, never as *answered* (no word on its cache).

The bridge: `claude agents --json` (Claude Code's list for scripts: id, pid, name like `dev-9a`, status idle/busy/waiting, waitingFor; a failure is a 500 with its message, never an empty list), + the console (tmux pane whose shell is — or is the parent of — the pid; a console not listed yet = `starting`), + the title (last `ai-title` in the last MiB of the transcript), + the advisor's file; advisor files older than 7 days are deleted (the advisor cannot). `POST /console` with `story` → `CONTEXT_STORY` in the session's environment; with `second` → `BRIDGE_SECOND_COMMAND` and the guard's hosts (`second.fix` → `BRIDGE_SECOND_FIX_COMMAND` in the worktree `POST /second/fix` made). `GET /sessions/answer?id=` → the session's last answer (`last_answer`: the text after its last tool call, '' while a prompt waits). `/second/fix` (POST prepare, GET state), `/second/fix/push`, `/second/fix/remove`: a fix's worktree (409 = refused: moved on, nothing to push, a rebase without force). Bridge API 8. `POST /console/end` returns once the console's Claude has exited (10 s max): it takes seconds, and a session seen meanwhile reads as one in another terminal. `POST /sessions/end {id}` ends a session in any terminal: SIGTERM to the pid `claude agents` lists for it, only if `ps` says it runs claude (a dead session's pid can be another program's: an error, never "ended"), then waits for it like a console (10 s, else an error); not listed = gone already. Claude restores the terminal and exits, its MCP servers with it; the shell and the transcript stay. `/clear` keeps the pid and changes the session id: the row stays on its console.

`board()` files the sessions (`live()`, 3 s cache) where you put them, else under the cycle's stories (`cycle.load()`: each big rock's epics, then the run) by the advisor's story — a console named `sc-N` (or `sc-N-xxxx`) is that ticket's until the advisor speaks; an alert's console (`zabbix-<event>`, `sessions.ALERT`) goes with the run while its story is not in the cycle (none yet, or a new ticket the cycle has not read) —, then your started stories without a session; your unstarted ones fold (`later`); the rest is *Off cycle*. Groups have keys (`_groups`: `rock:<title>`, `run`, `own:<id>`, `off`; DOM ids and folds follow them): your own sections sit between the run and off cycle, shown even empty. **Where you put a session** (`watcher_state` `sessions`: `sections` = `[{id, title}]`, `filing` = `{session key: group key}`, the latest `FILED_KEEP` moves, read-modify-write under `_layout_lock`) wins over its ticket and is kept after it ends — a console picked up again (`sc-N`) goes back there; a move to a group gone (section removed, big rock renamed) is ignored. `POST /api/sessions/file {key, group}` (409 on a group gone), `/api/sessions/sections {title, key?}` → `{key}`, `/sections/<id> {title}`, `/sections/<id>/delete` (its moves go). New offers every group (`under`, the run checked), filed unless off cycle. State: waiting > working/starting > done (idle, answered, cache warm) > idle (cache cold, or nothing answered since a `/clear`); the advice puts the size on the row. Row keys `console:<name>` / `session:<id>` / `story:<id>`; `_find` falls back from a ticket's key (`story:N`, `console:sc-N[-xxxx]`) to the row that now carries it (picked up, or its console ended). A console's row carries `data-term` and no `data-detail`: it shows on the board, never in the pane (a start lands there as *Opening on the board…* until the list selects it). The detail: a session elsewhere → its facts and **End**; a ticket → `shortcut.story` (state, open PRs, last comment whose first line says Handoff, else the last) + **Pick up** (`POST /api/sessions/start`: console `sc-N` linked to it — `sc-N-xxxx` when `sc-N` has moved on to another ticket —, prompt `sessions.resume_prompt` or `RESUME_PROMPT`, `{story}` only). A console's pane asks Shortcut nothing. **New** (`/api/sessions/new`): console named after the task's first words. Started → `HX-Trigger-After-Settle: select-key`, the next list poll selects it. **Start fresh** types the advisor's handoff command without Enter (`data-term-type`). Badge = sessions `waiting`; the nav asks the bridge on full pages only.

The page (`static/sessions.js`): each group is a `.proj` block (folded ones in localStorage, re-applied on the list's `htmx:afterSwap`, before paint), a ticket row is one line whose icon is its state (`sessions._glyph`: state type, plus the workflow's own words for review and blocked), **Live** hides the tickets (`#list.s-live`, CSS only). **Focus** = `.app.s-focus`: entered by a click or ⏎ on a session (`row-selected`, dispatched by `app.js` `select()`, carries the key; `select-key` after a start asks for it too), left by Esc, the grid button, a ticket selected, or the session gone from the list (not from a list that shows the bridge's error: one failed answer lists nothing); the sidebar becomes a rail (labels in `.l`), the list keeps the live sessions, or folds into a column of their icons (`.s-dock`, ⌥0, taken in the capture phase before xterm). A live row has a × (`data-close`, taken in the capture phase before its row), a console on the board its End (same attribute): `POST /api/sessions/end` with the row key (`console:` → the console ends, `session:` → `/sessions/end`), confirmed only when the session works, starts or waits; a session of another terminal shown in the pane answers there like End (its ticket back, or *Session ended*), anything else `quiet` → 204, then the list is fetched again and the board drops what ended. `htmx.ajax` gets the × as `source` (2.0.3 refuses a call with neither source nor target). The columns glide (`grid-template-columns` on custom properties): the selection mark waits for them to land, and console.js fits a terminal once its size has settled (every step would redraw Claude Code).

**The board** (`static/board.js`, in `.s-work` beside `#detail`; `.s-work.s-board` shows it): up to four consoles on a 2×2 grid — the whole board, two columns, a column split in two (`CELLS`, `LAYOUTS`), each slot absolutely placed so a change glides. A console row selected (click, ↑↓, a start) takes the active terminal's place, or the board when empty; one already there becomes active. Drag (pointer events, 5 px, the handle captures the pointer so xterm never sees it, the list is not polled meanwhile): a live row onto a terminal splits it while there is room (whole board → left/right half, a column → top/bottom), else replaces it; a terminal's head onto another swaps them, onto the list takes it off (like its ×: the session goes on); a live row — a console or a session of another terminal — onto another group of the list files it there, onto *New section* makes one with it (`section-made` → sessions.js opens its name), the pane left as it was; the box under the pointer says which, Esc calls it off, and the click that ends a drag never reaches the row. The board is this browser's (`localStorage` `sentinel.sessions.board`, `{slots: [{key, r}], active}`, read back only as one of `LAYOUTS`); a poll drops the terminals whose console is gone (not on a bridge error), copies each head from `#heads` (`<template data-key>` per console, rendered with the list) and draws on each row where its terminal is (`.where`, blue for the active one). A poll selecting again a session you took off leaves the board alone (`row-selected` acts on a new key, or on a click), and moves the list's selection only while the board shows (a ticket or New in the pane stays); a bridge away at load keeps the board (`.s-error`, as on a poll). `/sessions?open=<console>` (the URL is cleaned at once: a reload does not open it again) puts that console beside the active terminal (`join`: a whole board splits left/right, a column top/bottom, a quarter's neighbour column when the active one is a quarter, the active one's place at four) — at load, or on the poll that first lists it. Every terminal stays attached while the page lives, the board hidden or not, shows its console's name until its head comes, and reconnects on a click after a failed attach or a drop (not after a 404: ended); `⌥1–4` gives one the keys in reading order; clicking in one makes it active and moves the list's selection there (`app.js` `select(row, {load: false})`). An End that fails answers in `#detail` (HX-Retarget): the pane is shown. `app.js` ⏎ reads `#detail [data-open]` only for a row with a detail — a console's ticket is its row's `data-url`. `select-key` selects at once a row a poll listed already (the refresh would return the same list, never swapped).

**In the inbox** (`sessions.watch()`, every 30 s, source `claude_sessions` — `sessions` in `watcher_state` holds your sections, listed in Settings' jobs): a session `waiting` → row `wait:<id>` (urgency `later`, pushed after `session_wait_minutes`; `misses=1`: a wait answered leaves at once and the next one starts its own grace — `claude agents` gives no "waiting since"). A session *answered* (`done`: idle, answered, cache warm) is never a row — "nobody came back to it" cannot be seen, reading leaves no trace — but goes to `sessions.answered()` (subject, ref, title, url, `at` = its answer) for the mod's band. A bridge error records the failure: the rows stay, not promoted (seen more than a minute ago), `answered()` empties. Each push carries `renotify` (`sw.js`): a session's next wait reuses its item's tag. Rows link to `/sessions?open=<console>` (a console) or `/sessions`.

## The Second (second.py + contrib/claude-second-guard)

`second.tick()` (every 30 s, when `second.enabled` and a bridge): `_discover` queues jobs — one per (kind, subject, fingerprint) in `second_jobs`: `watch` (a pending Zabbix item older than `watch_minutes` and younger than `watch_hours`, fingerprint its `first_seen`, console `zabbix-<event>`; skipped when that console is open: yours), `stuck` (your started stories in the cycle data, `updated_at` older than `stuck_days`, no live session on them — `sessions.stories_at_work` —, and not untouched since the Second's own comment: `posted_at` = the story's `updated_at` right after it; at most `stuck_per_day` queued per local day, the longest stalled first; console `second-sc-N`, linked to the story), `plan` (weekday, local time past `plan_at`; console `second-plan-<date>`); `_follow` reads a running console's session (by console name) and, once it is idle with an answer (bridge `GET /sessions/answer`: the text after its last tool call, main loop only), files it: `done` + `_deliver` (`stuck` → `shortcut.comment`, which refuses a story you do not own; `plan` → an item `plan:<date>` of source `second_plan`, lane `plan`, urgency `now`, `misses=1` so yesterday's resolves, the source seeded first: a plan is news); a console gone before answering → `failed`; no answer after `timeout_minutes` → `late` (its place freed, still read later); `_start` starts queued jobs within `concurrency` and `max_per_day` (`console.start(..., second={ssh_hosts, curl_hosts})`); a console opened meanwhile → `failed` (yours); `_tidy` ends a console an hour after its answer when idle, not attached and its last answer is still the job's report — else `ended_at = 'kept'` (you went on in it); `_review` queues `deep` (agents, auto, daily cap) on reviews asked of you by name pending `review_days`. Prompts (`PROMPTS`, `second.prompts.<kind>` to override, `{read_only}` `{data}` `{lang}` + per kind) carry their material fenced (`BEGIN DATA <nonce>`); `stuck` adds what the board shows of the story (`shortcut.story`: PRs, last handoff). The alert's row shows *Second reading* / *diag ready* (`list_macros.second_tag`, `second.for_items`), its detail the report; the plan's detail is its report.

**Fixes** (`_fixes`, `fix_minutes` > 0): your open PRs from `my_prs` (drafts included — `next_action` files a draft as `draft` whatever it waits on, so the Second reads the raw fields), not from a fork (`cross`), not while a session of yours (a console not named `second-*`) works on the ticket in its branch (`sc-N`, `_story`), one job at a time per PR, `fix_per_pr` started a local day (a fix that failed to start does not count), and never more than `fix_per_pr` fixes in a row each started from the head the previous one pushed (`_own_streak`: a check its fixes keep red is not chased day after day; a push of yours resumes it). Its first pass (no `fix_seeded` in `watcher_state` second) records every token waiting as `fix_baseline` and queues nothing — turning fixes on does not take up the stock, only what comes after. What a fix takes up are **tokens** (`_asks`): `conflicts@<head>`, `ci@<head>`, `review:<id>` per review requesting changes and `thread:<id>` per open thread (`my_prs`: `change_reviews`, `open_threads`) unless approved — a review's asks are keyed on the review, not the head: the Second's own push leaves the review standing and its threads open, and must not bring them back. A job queues the PR's tokens no earlier job took (failed ones excepted) once the oldest has waited `fix_minutes` (`watcher_state` second/`fix_seen`, token → [first, last seen], rebuilt each tick: a token gone for `FIX_SEEN_KEEP_MINUTES` (15) is forgotten — the search drops a PR for a poll now and then); the fingerprint holds the attempt number (a failed start is queued again on the same tokens); after a failed start the PR waits `FIX_RETRY_MINUTES` (30), and a head the bridge refused (`meta.refused`: moved on — `my_prs` is a poll behind your push —, or a link leaving the repository) is not asked again while the cache still shows it; `meta` (JSON column) keeps repo, number, branch, base, head, draft, causes, tokens; console `second-<repo>-<n>-<k>`, linked to the story. `_start`: state `preparing` (counts in `concurrency`), then `_spawn` → `_open_fix` in a thread (a first clone takes minutes, the tick goes on; tests run it inline): `console.fix_prepare` → `POST /second/fix` (a ValueError = refused at that head → failed + `refused`), then `_open` = `console.start(..., second={…, fix: True})`; a console of that name open → failed (its worktree stays); `preparing` past `PREPARE_MINUTES` (30, `meta.preparing_at`: Sentinel restarted meanwhile) → failed. Prompt `PROMPTS["fix"]`: `FIXING` instead of `READ_ONLY`, `{review}` = `fix_review` or `REVIEW` (a devil's advocate read of its own diff). `_fix_done` on its answer: `console.fix_state` (commits, diff or range-diff, dirty, a rebase under way) into `meta.result`; nothing moved → a "changed nothing" comment; else `push(job, clicked=False)`. `push()` re-reads the worktree (`fix_state`: its session may have gone on since it answered) and the PR on GitHub (open, head = the fix's starting head, same repo, author = `github.login`), returns *waits for your push* on a PR under review unless `clicked`, holds back a draft whose diff or commit messages match `SECRETISH`/`PRIVATE` or whose diff was cut (`_held` → `meta.held`: the row asks for your push — what a draft pushes leaves the host unread, and review comments or CI logs may have steered it), then `console.fix_push(force=True)` — the bridge pushes leased on that head, so a rebase goes too; `meta.pushed/forced/by`, a "fix pushed" comment on the story (`_comment`: same SECRETISH/PRIVATE holds as `stuck`). `_fix_rows` → source `second_fix`, lane `fix`, one row per PR (its latest done job), `step` ready (a PR under review, or a held draft; urgency now: the only push) / pushed / refused / nothing / unread (quiet, still listed in Priority under *The Second*, not in Later's reminders); a row goes when the PR leaves `my_prs`, its head is neither the fix's start nor what it pushed, or its worktree was pruned unpushed (`_prune` runs first). `POST /api/second/<job>/push` = your click (`_fix_detail`: report, commits, diff, Push while ready). `_prune`: a worktree goes (`console.fix_remove`, `meta.removed`) once its console is gone and the job failed, pushed, was overtaken (PR gone, head moved) or finished `FIX_KEEP_DAYS` (3) ago.

The consoles (bridge `BRIDGE_SECOND_COMMAND`): `claude --restricted [--mcp-config …] --tools <reading tools + Bash> --permission-mode manual --model opus --effort medium --plugin-dir claude-second-guard --plugin-dir claude-code-context`. `--restricted` ignores user/project/local settings (allow rules, hooks, env, MCP servers): `BRIDGE_SECOND_MCP` passes MCP configs, **before** the other options (`--mcp-config` is variadic: last, it takes the prompt for a file). The guard (`policy.ts`, `check(tool, input, cfg)` → allow | refuse) answers every `tool.check` after the engine (`register.ts`): allow, or — while nobody wrote in the session (`$.session.turns() < 2`: the job's prompt is the first) — **deny, never ask**: an unattended `ask` waits on nobody, and a permission dialog offers "switch to auto mode", which hands every later ask to a classifier (seen live 26/10/2026 when the owner answered two dialogs). Once a person wrote in the console, the rest asks, as in any session. It never turns the engine's `deny` into an allow; its `.catch` denies. The `--plugin-dir` folders are watched: a merge on master reloads the guard in running consoles. reading tools allow (a path that looks like a secret asks), MCP tools allow when their name has a reading verb and no writing one, Bash goes through a small shell reader (`parse`: segments on `| && || ; &` and new lines, redirections, the variables each expands; command substitution, `$'…'`, subshells, heredocs, unclosed quotes → null → asks; a variable outside `SAFE_VARS` asks — it may hold a token) then each command against the list (`PLAIN`, per-command rules for flags and subcommands, `sudo`/`timeout` unwrap, `ssh` = allowed host (`-J` hops too) + the remote command re-read, curl = GET to localhost or `SECOND_CURL_HOSTS`, sed = only the forms of `SED_SAFE`, awk/jq = nothing that runs or reads the environment, grep not recursive and rg without hidden files, nothing over the whole home or disk (`everywhere`); a word that is a secret path (`SECRET`: keys, `.env`, `~/.config`, `.mcp.json`…) or dodges one with a glob or a brace asks); output redirections only to `/dev/null`. Two reviews broke it five times (awk `-e`, sed `w`/`r`, `~/.config`, `$'\x..'`, `jq env`, `base64 -o`): any new command or flag goes in with a test of what it must refuse. Egress: `_deliver` holds back a `stuck` answer that looks like it holds a token (`SECRETISH`) instead of posting it. `SECOND_SSH_HOSTS` / `SECOND_CURL_HOSTS` come from `second.ssh_hosts` / `curl_hosts` through `POST /console {second}` (patterns of `[A-Za-z0-9*._-]`). Without the guard loaded the session is still restricted and manual: everything asks. **A fix** (`BRIDGE_SECOND_FIX_COMMAND`: the same plus `Edit,Write,NotebookEdit`; `--restricted` confines the file tools to the working directory, the worktree; `--settings` attribution empty — your settings are not read, Claude Code would add a co-author trailer) gets `SECOND_WORKTREE` (absolute, at least three levels deep), `GIT_EDITOR=true` and `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1` (Bash back in the worktree after every command): `within()` = lexically inside it, `.git` excluded, a relative path counts from it — read whatever the name (a fresh checkout holds the repository and the fix), edited by the write tools; `commit()` lets `git add/rm/mv/restore`, `checkout -- <paths>`, `commit -m` (no `--amend`, `--author`, `-F`, `-t`, `-C/-c`; without `-m` it would abort on an empty message) and `rebase origin/<x>` (no `-i`, `-x/--exec`, `--root`, `--onto`, `-r`; `--continue/--abort/--skip`) run; a command with `cd/pushd/popd`, a git with global flags (`-C`, `--git-dir`…), `sudo` and `ssh` lose the worktree; `git push` is always refused. The bridge (`prepare_fix`): a bare blobless clone per repo under `BRIDGE_SECOND_ROOT/repos` (fetch refspec to `refs/remotes/origin/*`, so `origin/<base>` exists), the branch fetched and checked at the expected head, `git worktree add -B <console>` under `work/`, a `<console>.json` beside it (repo, branch, base, head, mirror, path, pushed); a checkout holding a symbolic link that leads outside it is refused and removed (`_links_out`: the guard judges paths by their letters and reads every name inside the worktree — a link to `~/.aws` would be read through), and so is a push while one is there (a rebase may bring one); a per-repo lock around fetch, worktree and push; `_trust` records the clone as trusted in `CLAUDE_JSON` (Claude Code keys a worktree's trust on its repository: verified 26/10/2026 — a new worktree folder shows the trust dialog, nobody answers it) — Claude Code takes no lock this side can share: replaced whole only if the file's mtime did not move since it was read, read back, up to 5 tries; `fix_state` also returns the commits' full messages (`messages`, scanned by `_held`) and `links_out`; `push_fix` refuses a dirty tree, a rebase under way, nothing new, a head other than the one it started from, a rewritten history without `force`, and pushes `--force-with-lease=refs/heads/<branch>:<head>`. `tests/test_bridge_fix.py` runs on the host against real repositories (the image has no git). `unroll` reads `for NAME in <literal words>; do …; done` as its body once per value (`$NAME` replaced, the ssh host then checked); while/if/until, nested loops or a list that expands are refused.

## API for the Claude Code mod

`GET /api/summary?since=<notification id>` → `attention`, per-section `counts`, `landing` (follow-up stages), up to 25 items needing you, sessions first (id, lane, ref, title, url, why, `subject` — a session's id for a session row —, `at` = when it began to need you: `notified_at`, else `first_seen`, claude headline), `answered` (`sessions.answered()`), notifications after `since`, `seq`. The mod's band above the prompt lists the items, then the sessions answered, whose `at` is after your last prompt in that session (`origin` composer or bridge only: a task notification, a teammate or a schedule does not move it), its own session left out, only while no turn runs (`AbovePrompt.isWorking`); toasts only when no surface the session draws on has that band. Item actions answer JSON unless the request comes from HTMX (`_done()`: the list, retargeted to `#list`, + `HX-Trigger-After-Settle: acted` so the page selects the next row): `POST /api/items/<id>/ack|unack|snooze|unsnooze` (snooze `duration`, default `tomorrow`), `POST /api/items/bulk {ids, action: ack|snooze}`.

## Adding a watcher

1 file in `watchers/` (class with `name`, `interval_seconds`, `fetch()` returning `WatchedItem`s with lane + urgency + a fingerprint that changes only when an ack should re-open), register it in `build_watchers()`, 1 block in `config.yaml`. Diff, state, grace, notifications are already handled. A source computing its own state (like my_prs/followup) calls `engine.process(name, items)` after `db.record_run(name)`.

## Conventions

- Commits: Conventional Commits, no Claude/Co-Authored-By signature
- DB timestamps: UTC ISO `%Y-%m-%dT%H:%M:%SZ`, local display via `localdt`, ages via `age`
- No application auth: bind `127.0.0.1:8300` only
- Public repo: no org names, logins or internal project names in code, docs, examples or screenshots (config.yaml/.env/data are gitignored; screenshots only from fake data)

## Gotchas

- Subscribe to push from `http://localhost:8300` (never `127.0.0.1`) and with Chrome/Firefox (Safari is finicky)
- `vapid_claims`: pass a fresh dict to every `webpush()` call (pywebpush mutates it)
- Never call a `db.*` helper that opens its own connection while holding a write transaction (`with db.connect() as conn:` after a write): the second connection waits on the lock for `busy_timeout` then fails — read `watcher_state` before the transaction, write it after
- Polled regions (`#list` every 20 s, `#watchers`, `#cycle`): `app.js` skips the swap when the HTML is byte-identical, otherwise keeps the list scroll, every open `<details id>` and the selected row (`data-key`). The detail pane is never polled — only Claude blocks poll themselves while a run works. Give any new `<details>` an id or it closes on the next poll
- `app/` is COPYed into the image, not bind-mounted: a template or Python change needs `docker compose up -d --build`
- Never open `data/sentinel.db` from the host while the container runs (WAL across the bind mount → `disk I/O error` in the app): `docker compose exec` or the API
- Jinja: a dict key named like a dict method (`items`, `keys`) resolves to the method — use another key (sections use `rows`)
- Bridge plist edits: `launchctl bootout` then `bootstrap` (`kickstart -k` keeps the old EnvironmentVariables). The bridge is a separate process: an upgrade of the app needs a bridge restart too, `check_bridge()` flags an old one
- Console: the page names the alert, Sentinel writes the prompt (`watch_views.api_zabbix_console`), the bridge passes it to the shell as `SENTINEL_PROMPT` (expanded, never parsed) and strips `BRIDGE_*` from the tmux server's environment. The WebSocket (`/console/ws`) takes no token: a ticket from `POST /console` (once, 60 s) + an Origin in `BRIDGE_ORIGINS` — keep both. `app.js` leaves every key typed in `#console` or a `.console-term` to the terminal (Escape included). A `.console-term` is `content-box`: xterm's fit reads the host's computed height as its room. `main.not_in_a_frame` (X-Frame-Options + frame-ancestors) is what stops a framing page from clicking Claude and typing for you — keep it. Zabbix fields enter the prompt through `watch_views._field` (one printable line, 300 chars). Watch's and the inbox's Claude buttons carry `data-session` (console.js: POST, then `/sessions?open=<name>`, the window closed if it showed that console); Settings' Open keeps the window (`data-console`). Links: Claude Code writes its own as OSC 8, which tmux drops unless the client terminal has the `hyperlinks` feature (`tmux.conf`, read only when the server starts: `tmux -L sentinel set -as terminal-features 'xterm*:hyperlinks'` on a running one); console.js opens them and the bare addresses (`addon-web-links`) on a left click, http(s) only
- A second bridge (a test instance) shares `tmux -L sentinel` with the first: it lists, attaches to and ends the same consoles
- `#detail` takes only the selected row's answer (`app.js` beforeSwap guard): a button filling the pane on its own (Sessions' New) carries `data-unselect`. `rows()` skips rows in a closed `<details>` — not `offsetParent`, Chrome keeps it on `content-visibility: hidden` content —, in a folded `.folded` block, and rows hidden by CSS (no client rects)
- Rendered markdown (Claude verdicts, GitHub comments) goes through `md.render` → nh3 allowlist: never mark untrusted HTML `|safe` any other way
